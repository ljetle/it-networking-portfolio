# Access Control Lists (ACLs)

## Overview
This lab focused on configuring and testing Standard and Extended Access Control Lists (ACLs) on Cisco routers using Cisco Packet Tracer and physical networking equipment.

We configured a Standard ACL to restrict traffic from a specific subnet, then implemented Extended ACLs to control traffic based on source and destination IP addresses, protocols, and port numbers. We tested connectivity using ping, HTTP access, and a UDP socket program. The network used OSPF to establish connectivity before the ACLs were applied.

## Objectives
- Configure Standard ACLs to filter traffic by source IP address.
- Configure Extended ACLs to filter traffic by source, destination, protocol, and port.
- Apply ACLs to router interfaces.
- Verify ACL behavior using `show access-lists`.
- Test network connectivity using `ping` and HTTP.
- Test traffic restrictions using a UDP socket program.
- Analyze permitted and denied traffic using ACL hit counts.

## Technologies and Tools
- Cisco Packet Tracer
- Cisco routers
- OSPF routing
- Standard and Extended ACLs
- IPv4 addressing
- `ping`
- `show access-lists`
- HTTP
- Python UDP socket programming
- Cisco IOS CLI

## Standard ACL Configuration

### ACL Rules

A Standard ACL was configured to deny traffic originating from the `192.168.71.0/24` subnet while permitting traffic from other sources.

```text
access-list 10 deny 192.168.71.0 0.0.0.255
access-list 10 permit any
```

The ACL was tested by pinging between PCs on different subnets and checking access to the web server.

## Extended ACL Configuration

Extended ACLs provide more specific traffic filtering than Standard ACLs because they can match source and destination IP addresses, protocols, and port numbers.

### Scenario 1: Block UDP Traffic on Port 13000

The first Extended ACL scenario blocked UDP traffic from the `10.1.1.0/24` network to the server at `170.1.1.1` on port `13000`. Other IP traffic was permitted.

The ACL was configured on Router 2, interface Ethernet 0, in the inbound direction.

```text
configure terminal
access-list 100 deny udp 10.1.1.0 0.0.0.255 host 170.1.1.1 eq 13000
access-list 100 permit ip any any
interface e0
ip access-group 100 in
```

### Scenario 2: Restrict Traffic by Host and Protocol

The second scenario applied different traffic rules to three PCs communicating with the server at `170.1.1.1`.

- **PC0 (`10.1.1.2`):** Permit UDP traffic to the server on the configured port while denying other IP traffic to that server.
- **PC1 (`10.1.1.1`):** Permit ICMP traffic to the server while denying other IP traffic to that server.
- **PC2 (`10.1.1.3`):** Deny UDP and ICMP traffic to the server.
- Permit other traffic not matched by the preceding rules.

The ACL was configured on Router 2, interface Ethernet 0, in the inbound direction.

## Key Takeaways
- Standard ACLs filter traffic based on source IP addresses.
- Extended ACLs provide more granular control using source and destination IP addresses, protocols, and port numbers.
- ACL rule order matters because traffic is evaluated against the configured entries.
- ACLs must be applied to the correct router interface and direction.
- `show access-lists` displays configured rules and their match counts.
- Ping and HTTP tests help verify whether traffic is permitted or blocked.
- UDP socket testing demonstrates how ACLs can restrict application traffic.
- OSPF can provide network connectivity while ACLs control which traffic is allowed across that network.

## Conclusion
This lab demonstrated how Standard and Extended ACLs can be used to control traffic across a routed network. The Standard ACL restricted traffic from a specific subnet, while the Extended ACL scenarios applied more specific rules to UDP and ICMP traffic.

Connectivity tests and ACL hit counts helped verify the effects of the configured rules. Overall, the lab reinforced the importance of ACL rule order, interface placement, and testing to ensure that network traffic is filtered as intended.
