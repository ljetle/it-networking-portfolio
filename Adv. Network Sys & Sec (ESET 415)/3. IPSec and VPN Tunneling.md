# IPsec VPN Configuration and Verification

## Overview

This project demonstrates the configuration and testing of a site-to-site IPsec VPN using Cisco Packet Tracer. The network was configured with three routers and multiple LAN subnets to establish connectivity between hosts across separate networks.

The project involved configuring IP addressing, OSPF routing, extended access control lists (ACLs), ISAKMP Phase 1 policies, IPsec Phase 2 parameters, and crypto maps. Connectivity tests and IPsec security association statistics were used to verify the tunnel and observe how traffic was encrypted.

## Objectives

- Configure router interfaces and assign IP addresses.
- Establish routing between network subnets using OSPF.
- Verify connectivity using ping and routing tables.
- Configure extended ACLs to identify traffic protected by IPsec.
- Configure ISAKMP Phase 1 and IPsec Phase 2 parameters.
- Apply crypto maps to router serial interfaces.
- Verify IPsec tunnel activity using `show crypto ipsec sa`.
- Compare packet headers and encapsulation across network interfaces.
- Distinguish between traffic protected by the VPN and traffic routed normally.

## Technologies and Tools

- Cisco Packet Tracer
- Cisco IOS CLI
- IPsec VPN
- ISAKMP/IKE Phase 1
- IPsec Phase 2 transform sets
- Extended Access Control Lists (ACLs)
- OSPF routing

- Packet PDU inspection

## IPsec VPN Configuration

The VPN was configured between Router 1 and Router 3. Extended ACLs defined the traffic considered interesting traffic for IPsec, and crypto maps were applied to the serial interfaces to activate IPsec processing.

### Phase 1: ISAKMP Policy

ISAKMP Phase 1 parameters were configured on both routers to establish the security negotiation between VPN peers.

The reported configuration included:

- ISAKMP policy number: `10`
- Encryption: AES
- Authentication: Pre-shared key
- Diffie-Hellman group: `2`
- Peer-specific pre-shared key configuration

The same shared key was configured on both peers. The key value is intentionally omitted from this public project README.

### Phase 2: Transform Set

A transform set named `VPN-SET` was created to define the IPsec protection parameters.

The reported configuration used ESP with 3DES encryption and SHA-based authentication, as reflected in the IPsec security association output.

### Extended ACLs

The extended ACLs identified traffic between the two protected LANs.

- **ACL 120 on Router 1:** Matched traffic from `192.168.3.0/24` to `192.168.5.0/24`.
- **ACL 110 on Router 3:** Matched traffic in the reverse direction.

These ACLs defined which traffic should trigger IPsec encryption. Traffic that did not match the protected subnet pair was not encrypted by this VPN policy.

### Crypto Map

A crypto map named `VPN-MAP` was configured on both routers. The maps referenced the appropriate peer address, transform set, and traffic-matching ACL.

The crypto map was then applied to the routers' serial interfaces, enabling IPsec processing for matching traffic.

## IPsec Tunnel Verification

The command below was used to inspect the IPsec security associations and packet counters:

```text
show crypto ipsec sa
```

Three sets of results were captured to observe the tunnel before and after traffic was sent.

### Before Protected Traffic

Initially, the encapsulation, encryption, decapsulation, and decryption counters were all zero. This indicated that no matching traffic had yet passed through the IPsec tunnel.

### After Pinging PC-C

After traffic was sent from PC-A to PC-C, the encapsulation, encryption, decapsulation, and decryption counters increased to three.

This showed that traffic between `192.168.3.0/24` and `192.168.5.0/24` matched the crypto ACL and was processed through the IPsec tunnel.

### After Additional Traffic

After additional pings were sent toward PC-B, the IPsec packet counters did not increase further.

The report explains that traffic between PC-A and PC-B did not match the configured crypto ACL. Consequently, this traffic was routed normally rather than being encrypted by the VPN.

## Testing Protected and Unprotected Traffic

The ping tests demonstrated the difference between traffic that matched the VPN policy and traffic that did not.

| Test | Destination | Result | IPsec Behavior |
|---|---|---|---|
| PC-A to PC-C | `192.168.5.3` | Successful replies after an initial timeout | Matches the protected subnet pair |
| PC-A to PC-B | `192.168.4.3` | Successful replies in the recorded output | Does not match the protected subnet pair |

The report's Question 4 describes PC-A as being able to reach PC-C but not PC-B. However, the included ping output shows successful replies from `192.168.4.3`. The accompanying explanation and IPsec counters support the distinction that PC-A-to-PC-B traffic was not encrypted by the configured VPN policy.

This illustrates that VPN encryption policies and ordinary network reachability are separate concepts. Traffic excluded from an IPsec ACL may still be able to reach its destination through normal routing.

## Packet Header Analysis

Packet PDU details were inspected to observe packet information as traffic moved through the network.

The captured host-side outbound PDU showed Ethernet II encapsulation. The router-side PDU showed HDLC encapsulation on the serial link.

The visible packet details included:

- Source IP address: `192.168.3.3`
- Destination IP address: `192.168.5.3`
- Protocol: ICMP
- TTL on the host-side outbound packet: `128`
- TTL in the captured router-side packet: `127`

The source and destination IP addresses remained the same in these displayed packet details, while the TTL decreased by one as the packet passed through a router. The link-layer encapsulation also differed between the Ethernet and serial interfaces.

These captures demonstrate changes in link-layer encapsulation and the IP header's TTL during forwarding. The displayed PDU screenshots do not, by themselves, show the complete outer ESP packet header used for IPsec tunnel-mode encapsulation.

## Key Takeaways

- OSPF routing provides network reachability between routers and remote LANs.
- IPsec uses security policies and ACLs to determine which traffic is protected.
- ISAKMP Phase 1 establishes the security negotiation between VPN peers.
- Phase 2 transform sets define the IPsec protection parameters.
- Crypto maps associate peers, transform sets, and traffic-matching ACLs with router interfaces.
- The `show crypto ipsec sa` command helps verify security associations and observe encrypted and decrypted packet counters.
- Traffic excluded from the crypto ACL can still be forwarded through normal routing.
- Packet inspection helps demonstrate changes in TTL and link-layer encapsulation as packets traverse a network.

## Conclusion

This project demonstrated the configuration and verification of a site-to-site IPsec VPN using Cisco Packet Tracer. OSPF was used to establish routing between the network subnets, while extended ACLs identified the traffic to be protected by IPsec.

ISAKMP policies, IPsec transform sets, and crypto maps were configured to establish the VPN between Router 1 and Router 3. The `show crypto ipsec sa` outputs showed that packet counters increased when traffic matched the protected subnet pair and did not increase when traffic was outside that policy.

The project reinforced the relationship between routing, access control, VPN configuration, and packet encapsulation, while providing practical experience troubleshooting network connectivity and verifying encrypted traffic.
